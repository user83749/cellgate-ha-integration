# TECH7Fox Asterisk review for CellGate

Historical evaluation preceding the 0.4.0 implementation. For the shipped architecture, see [current call/media details](call-media.md).

Reviewed and evaluated November 2, 2026. Source inspection was followed by an isolated Linux/Docker lab using the referenced add-on image and synthetic credentials. No owner Home Assistant instance or CellGate service was accessed, and no physical gate command was sent. The production integration remains unchanged.

## What the repositories actually provide

| Component | Actual role | Consequence for CellGate |
| --- | --- | --- |
| Asterisk add-on | Runs Asterisk 22.11.0/PJSIP with SIP transports and an RTP/media engine | A candidate replacement for our limited handwritten SIP signaling, not just reference Python code |
| Asterisk HA integration | AMI client; discovers SIP/PJSIP endpoints; exposes registration, device/connected-line and DTMF sensors, plus an AMI action service | A control/status integration, not a native HA camera or an audio/video bridge |
| SIP browser card | Separate client connects to the PBX over WebSocket/WebRTC | Useful with a PBX, but does not replace the persistent native camera entity requested here |

The HA integration's platform list contains only sensors and binary sensors. There is no camera platform, native WebRTC offer handler or SIP credential provisioning for CellGate. Its `client.login()` authenticates to the Asterisk Manager Interface, not Home Assistant's user-login endpoint.

## Registration and call initiation

The add-on generates local extensions for HA persons. Its default dialplan rings registered contacts for an extension. This is not an existing CellGate cloud trunk.

Asterisk supports a separate outbound registration, authentication, provider endpoint, address-of-record and inbound endpoint identification. In principle these can represent the mobile-provisioned CellGate SIP account, followed by a dialplan route to local clients. Successful registration still does not establish inbound routing or media reachability.

CellGate's observed registration is provider-specific: the initial server returns `302` with a public-IP/port next hop; authentication succeeds there while the original account identity/Request-URI is retained. This must be tested explicitly before using Asterisk as a replacement. The inspected Asterisk 22.11.0 outbound-registration response handler has no explicit redirect-follow branch and treats otherwise unhandled failures as fatal/retry responses. The isolated lab below confirmed this behavior for a synthetic equivalent; actual CellGate interoperability is still unverified. A resolved outbound-proxy/next-hop configuration may be needed, with identity preserved and failover behavior understood.

No outbound cloud registration, provider identification or CellGate routing is generated by these repositories as supplied. Installing them alone would not connect the gate.

## Media and NAT

The generated browser endpoint template configures `webrtc=yes`, enabling DTLS/ICE/RTCP-mux behavior; it also sets `rtp_symmetric=yes`, `force_rport=yes`, `rewrite_contact=yes` and `direct_media=no`. The latter keeps Asterisk in the media path. RTP configuration enables ICE and Google STUN. Separate UDP, TCP, TLS and WSS transports are present.

The template permits G.711/G.722/Opus and other audio codecs. Its optional video list contains H.264/VP8/VP9; `video_support` defaults to false. The add-on also builds audio codec modules rather than implementing an audio bridge inside HA Python.

Important limits:

- Asterisk generally forwards compatible video rather than transcoding it. Both legs must agree on video codec/format; an incompatible CellGate/browser combination still needs a video transcoder.
- The add-on docs retain a warning that SIP-card video is not working, while current templates configure video codecs. The isolated lab below demonstrated actual H.264 decoding at an aiortc WebRTC client, resolving the engine-level question for that format. It does not validate their SIP card or an actual HA/browser frontend.
- A native HA camera adapter is still required. AMI sensors/actions do not carry video or microphone media.
- The bundled RTSP/SIP module is not evidence that CellGate exposes an RTSP stream. No CellGate RTSP URL has been established.
- Local extension `max_contacts` values do not prove that CellGate allows multiple simultaneous cloud registrations alongside its iOS app.

Our current bridge already implements several analogous behaviors: RTP port learning from the negotiated IP, SIP rport handling, WebRTC ICE, actual-socket STUN discovery and separate SIP/viewer lifetimes. Its limits remain narrower: IPv4/UDP signaling, limited encryption/codec profiles, no SIP session-timer/re-INVITE renegotiation, no TURN relay configuration, and a restricted set of trusted SIP source addresses. The source review does not establish that those limits are causing a current device failure.

## Entity and authentication implications

Asterisk's call-state sensors are PBX/channel state, not the gate's physical open/closed state. They do not replace the mobile-API gate cover. The persistent HA camera can remain the product interface regardless of the underlying SIP backend.

The add-on's optional ingress registration uses its Supervisor-issued token to publish an ingress entity through Supervisor. That is a different boundary from browser camera tokens or a Home Assistant password login. It should not be copied into this custom integration as a workaround for camera authentication.

The 0.3.1 camera-authentication mitigation remains appropriate: no unnecessary snapshot URL, no camera recreation during intercom-option changes, and no errors for late candidates. These repositories do not supply a reason to undo it.

## Assessment

These projects are useful because Asterisk/PJSIP is an existing full SIP/media engine that could substantially reduce the interoperability surface maintained in our experimental receiver. Asterisk is a serious backend candidate if a separate service/add-on is acceptable.

It is not a drop-in solution: CellGate registration redirect behavior, inbound routing/source identification, simultaneous app operation, common video formats and a native HA camera/media adapter all require validation. No production architecture migration was performed, and no new production bug was demonstrated that justified another code hotfix. Test-only dependencies and the add-on image were installed on an ephemeral GitHub Actions runner.

Keep the standard HA gate cover and persistent camera interface. Evaluate a PBX backend separately from that interface, using a synthetic provider/redirect test first and a coordinated real incoming call afterward. The current integration's real incoming CellGate audio/video path remains unvalidated.

## Runtime findings

The [final isolated evaluation](https://github.com/user83749/cellgate-ha-integration/actions/runs/41526839868) passed on Linux amd64. It exercised Asterisk 22.11.0 from `ghcr.io/tech7fox/asterisk-hass-addon:6.4.0`, image digest `sha256:0a7bc9e15c43d087ae15072e01dfd32db78c2095fccd5f5ffa246b31046ad6ae`. The machine-readable summary is [asterisk-lab-report.json](asterisk-lab-report.json); full logs/SDP/channel evidence are workflow artifacts.

| Test | Observed result |
| --- | --- |
| Initial registrar returns SIP 302 | One front-end registration, no request to redirected server; not registered |
| Pre-resolved loose-route outbound proxy | MD5 digest challenge/authentication succeeded; original Request-URI and account identity retained |
| Incoming provider call | INVITE routed to registered local SIP-over-WebSocket endpoint; answered successfully |
| Provider H.264 to WebRTC | Actual frames decoded at 160 x 120, constrained-baseline H.264 packetization mode 1 |
| Provider PCMU to WebRTC Opus | Actual audio decoded; WebRTC endpoint allowed Opus only, forcing audio transcoding |
| WebRTC microphone to provider PCMU | Decoded return audio contained the microphone's 900 Hz tone, distinct from incoming 400 Hz audio |
| Close WebRTC media without SIP BYE | Both SIP channel legs remained Up during a two-second observation |
| Remote caller BYE | Hang-up propagated to the local SIP endpoint |

The loose-route parameter must be escaped as `\;lr` in Asterisk configuration; an unescaped semicolon begins a configuration comment and changes routing semantics. Redirect resolution was supplied by the lab, not performed by Asterisk. A production adapter must discover/validate the next hop and handle changes rather than hardcode an observed server address.

This confirms that the referenced image can perform the necessary *class* of SIP-to-WebRTC media bridging, including actual H.264 and bidirectional audio. It is a technically viable backend candidate and would replace much of the handwritten SIP/RTP engine. It does not make the two linked projects a complete CellGate integration.

The lab bypassed Supervisor startup and generated minimal PJSIP configuration; it did not validate the add-on's default configuration or auto-provisioning. All peers were on one runner with host ICE candidates. The WebRTC client was aiortc, not an HA frontend or iPhone. No Internet NAT/TURN, live CellGate call, real codec offer, app coexistence, ARM64 execution, renewal/failover, long-call behavior, or viewer reopen was tested. Media detach survival for two seconds is not a complete implementation of the requested HA call lifetime.

## Recommended implementation boundary

Keep the existing mobile-API cover and persistent native camera entity. If adopting Asterisk, run it as a separate SIP/media service and add a backend adapter in the custom integration:

1. Obtain the SIP configuration from mobile login, resolve the provider redirect, and configure a dedicated registration/trunk with controlled refresh and cleanup.
2. Report incoming-call state to HA without answering immediately; opening the camera answers the ringing call.
3. Maintain one backend SIP/media session for the intercom call. Relay video/audio to HA viewers and microphone audio back to that same call. Viewer closure releases its viewer resources; caller BYE ends the backend session.
4. Prove attach/reopen behavior through the native HA WebRTC camera API, including late ICE and concurrent viewers, before shipping.
5. Validate one coordinated real incoming CellGate call, recording negotiated codec/encryption/NAT behavior without publishing credentials.

The upstream Asterisk HA integration's AMI sensors are optional management conveniences; they are not the native camera adapter. There is no need to change gate cover semantics or introduce HomeKit-specific behavior. A separate Asterisk service is an architectural dependency that would need installation/configuration; this evaluation has not installed one on the owner's HA system.
