# Mobile call investigation — November 2, 2026

## Findings

The Android CellGate 4.0.61 package contains a Flutter application and native Linphone SIP call handling. Its native account setup explicitly uses UDP. The call path recovered so far is:

```text
Mobile API authentication / SIP detail retrieval (request contract unresolved)
    → saved sip_username / sip_password / sip_host
    → Linphone AuthInfo and Account
    → SIP server address configured with UDP
    → incoming call
    → create call parameters, enable video, accept call
    → receive video and use the microphone for conversation
```

This is static evidence from the Android artifact. It is not a captured call and does not prove that the current iOS version has identical implementation or that a second client can register safely with the same account.

## The owner's captures

- The first HAR contains 15 records. It has no transaction to `cellgate.zapopen.com` and no decrypted gate-control request.
- The second contains 31 records. Its original record 0 is a decrypted `POST` to Firebase's `/v1/firelog/legacy/batchlog`. Base64-decoding its protobuf body reveals the literal `com.cellgate.mobile`. This confirms CellGate-associated logging in that record; it is not the video stream or the gate-control payload.
- Neither export contains a transaction to `cellgate.zapopen.com`.
- The supplied iOS App Privacy Report screenshot lists `cellgate.zapopen.com` with 32 contacts. That report and the HARs have different collection scopes and do not by themselves identify the transport used for those contacts.

Proxyman documents that Flutter applications can bypass the system proxy. The Android package's Flutter implementation makes that a plausible explanation for the missing mobile API traffic. It is not proof of the cause on the owner's iPhone, and the absence of those requests is not proof that the owner configured Proxyman incorrectly. SIP/UDP is also outside ordinary HTTP request inspection.

Source: [Proxyman's Flutter note](https://proxyman.com/docs/debug-devices/ios-device#flutter-app).

## Mobile API leads

These exact literals were recovered from the compiled Dart string objects in `libapp.so`:

| Literal | Status |
| --- | --- |
| `https://cellgate.zapopen.com/` | Base URL literal; also present in native Java client construction |
| `api/CellCam/Login` | Endpoint literal; method/body/response not yet traced |
| `api/CellCam/GetSipInformationForUser` | Endpoint literal; authentication/parameters/response not yet traced |
| `api/CellCam/RefreshSIPToken/` | Endpoint literal; lifecycle and request contract not yet traced |
| `sip_username`, `sip_password`, `sip_host` | Read by the native SIP account configuration method |
| `registerSIPAccount`, `unRegisterSIPAccount`, `getSIPRegistrationStatus` | Native bridge methods advertised by the Android plugin |

The mobile API is distinct from the web portal API used by the current Home Assistant gate-trigger implementation. No authenticated mobile API request, SIP registration, call acceptance, or relay command was performed during this investigation.

## Native call trace

JADX 1.5.6 recovered the following call-handling code in simple pseudocode mode:

- `u8/g.java`, method `a()` / log label `configureAccount`, lines 177–258: reads the three SIP settings, constructs `sip:<username>@<domain>`, creates Linphone authentication info, sets `TransportType.Udp`, and creates/adds the account.
- `u8/b.java`, `invoke`, lines 77–110: creates parameters for the current call, enables video, and calls `acceptWithParams`. It can enable low-bandwidth mode for a slow mobile connection.
- `u8/d.java`, `onGlobalStateChanged`, lines 150–170: disables local video capture and enables video display. This is consistent with receiving gate video without sending the resident's camera video.
- `u8/d.java`, `onLastCallEnded`: resets call-related state and restores microphone availability for the next call.

The native library split contains `liblinphone.so`, `libmediastreamer2.so`, `libortp.so`, and `libsrtp2.so`. Their presence does not establish the negotiated codecs or whether a particular call encrypts media.

## Independent portal evidence

The downloaded portal code independently references:

`https://voicevideocall.zapopen.com/api/EVOhttp/GetSipInformationForUserFromAsterisk?UserID=...`

Its result is used to display a **Registered User** indicator in call-group management. Do not mistake this status endpoint for the mobile SIP credential retrieval endpoint.

The dashboard bundle also contains a separately gated `Live Stream` UI with `IsSupportLiveStream`, a media base URL variable, and `/Play?modulePortID=...`. The base URL is uninitialized in the traced view-model initialization, and the owner's visible dashboard did not expose this control. This does not establish working on-demand video for the owner's hardware/account.

CTG's published QA case study describes a mobile SIP registration, SIP INVITE, and RTP call flow and labels its illustrations as CellGate. This corroborates the general architecture but does not supply account-specific server details or credentials. [CTG case study](https://www.ctg.com/case-studies/security-products-manufacturer-quality-assurance).

## Provenance and limitations

Package: `com.celaccess`, version `4.0.61`, code `105185`, acquired from the APKPure distribution mirror for static analysis. The base APK independently downloaded and the base APK inside the architecture bundle are byte-identical. The APK's declared v2/v3 content digests are self-consistent; this is not independent authentication of the vendor's signing identity. The app was never installed or executed.

The JADX archive digest was checked against its official GitHub release. JADX completed with errors in some methods; observations here are bounded to the recovered excerpts. REA's Android decompiler provider was unavailable, so the Java analysis is from the standalone official JADX tool, not a successful REA Android decompilation.

See [mobile evidence](mobile-evidence.json) for hashes, exact string offsets, and trace coordinates, and [capture summary](capture-summary.json) for capture hashes and parser limitations. Raw captures, compiled binaries, and decompiled files are local research artifacts excluded from Git.

## What remains before camera implementation

The investigation has identified the call stack and credential-setting names. The remaining gap is the authenticated mobile SIP provisioning contract: how the login session obtains the actual SIP server, username, password, token, expiry, and any push/wake association. After that, client-registration behavior and negotiated media need validation before implementing a Home Assistant camera and two-way audio.

No camera entity has been added because those contracts are not verified. At this stage of the investigation the trigger implementation was still web-based. The subsequent version 0.2.0 migration replaces it with mobile login, discovery, and momentary gate commands; see [route inventory](mobile-routes.md). No additional phone capture or paid capture software is required to preserve or review the current findings.
